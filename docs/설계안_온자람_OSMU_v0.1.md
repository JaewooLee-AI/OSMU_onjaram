## 1. 제품 정의

"메모와 사진 한 벌 → 블로그 · 카드뉴스 · 쇼츠 3채널 콘텐츠" 를 온자람 브랜드 규칙대로 만드는 Windows 데스크톱 앱.
사용자는 **주제·메모·사진만** 넣고, 형식·규격·어조·CTA는 브랜드 킷이 기본값으로 정합니다.

핵심 원칙
1. 선택지를 줄인다: 기본값으로 끝까지 가고, 바꾸고 싶을 때만 "고급"을 연다.
2. 비용이 드는 단계는 실행 전에 예상 비용을 보여 주고, 사용자 이미지가 있으면 AI 호출을 건너뛴다.
3. 모델·단가·종류(카드 형식)를 코드에 박지 않고 데이터로 둔다.
4. 외부 계정이 필요한 기능(네이버 API·게시 자동화)은 없어도 핵심 흐름이 끝까지 돌아야 한다.

## 2. 아키텍처

### 2.1 베이스와 이식

- 베이스: `OSMU_cjc` 를 복사해 이 폴더(`OSMU_onjaram`)에서 새 저장소로 시작(비공개 권장 — 사업자번호·연락처·가격이 킷에 들어감).
- `ammasarang_card_shorts` 에서는 **UI가 아니라 서비스만** 이식: `card_renderer`, `shorts_renderer`, `shorts_from_cards`, `tts_gemini`, `omni_video`, `image_generator`, `media_assets`, `fonts`, `design_templates`, `design_proposals`, `review_sheet`, `source_check`, `compliance`.
  - 이유: Flet 버전이 다르고(1.0.2 vs 1.0.4) 화면 구조가 다름. cjc는 빌드 호환 때문에 flet 1.0.2·`jni_flutter 1.0.3` 고정 중.
- 이식하면서 바꿀 것: 파일/JSON 저장(`project_store`, `brand_kits/*.json`, `usage.jsonl`, `prices.json`, `keys.json`) → cjc의 SQLite·암호화 키 저장·`usage_log` 로 통일.

### 2.3 화면 구성 (내비게이션)

`홈` · `새 콘텐츠` · `내 콘텐츠` · `브랜드 킷` · `게시` · `설정`

- **새 콘텐츠**: 한 화면. 주제 + 메모 + 사진/영상 업로드 → [만들기] → 결과 탭 `블로그 | 카드뉴스 | 쇼츠`(당근은 2차에 탭 추가).
  고급(접힘): 카드 종류, 카드 장수, 템플릿 비율, 보이스 트랙, AI 이미지 사용 여부, 모델 지정.
- **내 콘텐츠**: 목록·상태(초안/확정/게시). 캘린더 대신 단순 목록.
- **게시**: 네이버 반자동 게시(Windows·Playwright). 없어도 "복사해서 붙여넣기" 로 마무리 가능해야 함.
- **설정**: 모델 등록(§7), API 키, 비용·예산, 선택 기능(네이버 API) 접힘.

## 3. 3단 템플릿 (이번에 확인한 신규 포맷)

치과병원 사진 4장의 공통 구조: `상단 텍스트 / 중앙 미디어 / 하단 텍스트`. 중앙이 영상이면 쇼츠, 이미지면 카드뉴스. 정보형은 중앙에 인포그래픽.

```jsonc
{
  "id": "tri-2-5-3",
  "name": "3단 (2:5:3)",
  "layout": "tri",
  "ratio": [2, 5, 3],            // 상:중:하 (프리셋 1:1:1, 2:5:3, 2:3:2 … 사용자 수정 가능)
  "top":    { "role": "title",   "max_lines": 2, "accent": "first_line" },
  "middle": { "slot": "media",   "accepts": ["image", "video", "infographic"], "fit": "cover" },
  "bottom": { "role": "byline",  "fields": ["author", "affiliation"], "logo": true },
  "overlay": { "caption": true, "qr": true, "panel": null },   // 사진 4장의 사진 속 캡션·QR·왼쪽 자막 패널
  "canvas": { "card": [1080, 1350], "shorts": [1080, 1920], "shorts_safe_margin": 250 },
  "colors": "brand"               // 기본은 브랜드 킷 토큰(세이지 그린·네이비·코랄·크림)
}
```

- 카드(4:5)와 쇼츠(9:16)가 **같은 템플릿 규격**을 공유하고 캔버스 크기만 다릅니다. 쇼츠는 상하 250px 안전 영역을 비웁니다(문서 규격).
- 현재 렌더러의 `gov`, `top_photo`, `illustrated` 레이아웃이 가깝습니다. `tri` 를 새 레이아웃으로 추가하고 비율을 파라미터화하는 방식(확인 필요: 기존 레이아웃 함수 재사용 가능 범위).
- 중앙 슬롯 `infographic` 하위 유형: `steps`(번호 단계, IMG_2021), `big_number`, `comparison`, `checklist`, `icon_grid`, `timeline`. §6의 아이콘 라이브러리로 **AI 호출 없이** 그립니다.
- 미디어 슬롯 우선순위: 사용자 업로드 → (설정 시) AI 생성 → 없으면 타이포 카드. §6 참고.

## 4. 파이프라인

```
입력(주제·메모·사진/영상)
 → ① 비식별 일반화 (개별 사례 제거, 보편 심리교육 콘텐츠로 변환)   ← 문서 §2.2, 맨 앞
 → ② 컴플라이언스 선검사 (counseling 팩: 낙인·단정·치료 보장 표현)
 → ③ 블로그 초안 (보이스 트랙 A/B)  → 카드 스토리보드 → 쇼츠 대본
 → ④ 미디어 배치 (업로드 우선 → 부족분만 AI)
 → ⑤ 렌더링 (카드 PNG / 쇼츠 MP4)  → ⑥ 확정 → 내보내기·게시
```

- 카드뉴스는 **블로그 초안과 같은 원천**에서 만들고, 쇼츠 대본은 "확정된 카드"에서 변환합니다(card_shorts의 기존 흐름 유지: 카드 수정 → 확정 → 대본 → 렌더).
- 팩트 락(원문에 없는 수치 금지)은 가격·연락처·인증번호에 그대로 적용합니다. 킷의 고정 팩트는 회사 문서·사용자 입력만 사용.

## 5. 카드뉴스 종류 확장 옵션 (요청 반영)

### 5.1 현재 문제
`card_shorts` 는 카드 형식이 `services/card_formats.py` 의 파이썬 딕셔너리이고, 형식마다 `ai_director._rule_based_<id>` 와
프롬프트 문구, 렌더러의 슬라이드 종류(`cover/body/numbered/big_number/comparison_table/event_info/call_to_action/single`)가 코드에 묶여 있습니다.
"준비 중" 7종(Q&A, 체크리스트, 스토리텔링, 텍스트 위주, 단계별 안내, 퀴즈, 메신저, 파노라마)은 표시만 되고 코드가 없습니다.
→ 종류를 하나 늘릴 때마다 코드 수정이 필요한 구조입니다.

### 5.2 목표 구조: "카드 종류 팩" (데이터 기반)
업종 규칙 팩(`compliance_packs/*.json`)과 같은 방식으로 **종류 하나 = JSON 파일 하나**. 코드 수정 없이 추가합니다.

```jsonc
// card_types/checklist.json
{
  "id": "checklist",
  "name": "마음 체크리스트",
  "status": "available",                 // available | draft | hidden
  "fit": "독자가 자신의 상태를 점검하도록 돕는 원고(진단이 아님)",
  "desc": "공감 체크 항목 → 해석 → 작은 실천",
  "template": "【주제 한 줄】\n체크 1: 【…】\n체크 2: 【…】\n…\n작은 실천: 【…】",
  "tips": ["항목은 3~5개", "진단·판정 표현 금지"],
  "count": { "min": 5, "max": 8, "default": 6 },
  "sequence": [                           // 장 구성. 슬라이드 원형(archetype)을 순서대로 지정
    { "archetype": "cover",     "hint": "질문형 헤드라인" },
    { "archetype": "checklist", "repeat": "1-2", "hint": "체크 항목 3~4개씩" },
    { "archetype": "body",      "hint": "왜 그런 마음이 드는지(자책 덜기)" },
    { "archetype": "steps",     "hint": "오늘 할 수 있는 작은 행동 3가지" },
    { "archetype": "cta" }
  ],
  "layout_default": "tri-2-5-3",          // §3 템플릿 id (사용자 변경 가능)
  "llm_structure": "…(프롬프트에 들어갈 구성 지침. 원문에 없는 수치 금지 등)",
  "fit_check": { "need_any": ["체크", "해당", "느끼"], "min_hits": 2 },  // 원고 적합성 경고 규칙(정규식/키워드)
  "shorts": { "hook_from": 1, "max_scenes": 6 },       // 이 종류를 쇼츠로 바꿀 때 힌트
  "compliance_extra": ["이 체크리스트는 진단이 아닙니다 고지 문구 필수"]
}
```

- **슬라이드 원형(archetype) 레지스트리**: 렌더러에 `cover, body, numbered, big_number, comparison, event_info, cta, single` + 신규 `checklist, steps, qa, quote, timeline, icon_grid, quiz` 를 **등록 방식**으로 둡니다(`@register_archetype("checklist")`).
  JSON 팩은 기존 원형을 조합하는 것만으로 새 종류가 되고, 진짜 새로운 모양(예: 메신저 화면)만 코드 1함수를 추가합니다.
- **규칙 기반 대체 생성(키 없을 때)** 도 팩의 `sequence` 로 일반화해 종류별 파이썬 함수를 없앱니다.
- **사용자 UI**: 설정 > 카드 종류 — 목록, [복제해서 수정](이름·장 구성·작성 틀·팁·장수), [JSON 가져오기/내보내기], [숨기기]. 초안(draft) 종류는 새 콘텐츠의 고급 목록에서만 보이게 합니다.
- **참조 이미지로 종류 만들기**(기존 `design_proposals` 의 확장): 마음에 드는 카드뉴스를 올리면 AI가 장 구성·원형 조합을 `draft` 팩으로 제안합니다. 올린 이미지는 분석에만 쓰고 저장하지 않음(기존 정책 유지).
- 안전장치: 팩 로드 시 스키마 검증(없는 archetype, 장수 범위 오류는 로드 거부 + 사유 표시). 사용자가 만든 팩이 앱을 깨뜨리지 않도록.

## 6. 사용자 이미지·영상 우선 모드 (비용 절감)

현재 `card_shorts` 는 이미 사용자 첨부 에셋(`asset_id`)을 쓰고 **없는 슬라이드만** AI 이미지로 채웁니다(`fill_missing`). 이를 명시 옵션으로 만듭니다.

- 이미지 소스 모드 (콘텐츠마다, 기본값은 설정에서):
  1. **내 사진만** — AI 이미지 호출 0회. 사진이 모자란 카드는 타이포·인포그래픽(아이콘) 카드로 렌더.
  2. **내 사진 우선, 부족분만 AI** (기본)
  3. **AI 생성 우선**
- 업로드 이미지를 카드/장면에 **수동 배치**(드래그 또는 목록 선택). 한 이미지를 여러 슬라이드에 재사용(다른 크롭).
- 쇼츠: 업로드 영상은 구간(start/end) 자르기 후 사용, 업로드 이미지는 켄 번스 효과. **AI 영상(Omni 등)은 기본 꺼짐**이고 실행 전 비용 확인.
- 인포그래픽용 **번들 아이콘 세트**(라이선스 확인된 것) + 브랜드 색 팔레트로 AI 일러스트 없이 `steps / checklist / icon_grid` 렌더.
- 실행 전 비용 미리보기: 업로드 이미지로 채워진 슬롯은 0원, AI로 채울 슬롯만 예상 금액에 포함.
- 사진 분석(비전)도 비용이 드는 호출이므로 "사진 설명 자동 분석" 을 켜고 끌 수 있게 하고, 끄면 사용자가 캡션을 직접 입력.
- 개인정보: 내담자 얼굴·이름이 보일 수 있는 사진 업로드 시 경고 문구(외부 AI 전송 여부 표시). 확인 필요(법무).

## 7. 모델 등록 시스템 (하드코딩 제거)

### 7.1 현재
- `cjc`: `multi_llm_router` 에 공급자별 기본 모델명, `model_prices` 표는 있으나 모델 목록은 코드 상수.
- `card_shorts`: 이미지(`GEMINI_IMAGE_MODELS`), TTS(`GEMINI_TTS_MODELS`), 영상(`OMNI_MODEL`, `PRICE_PER_SEC`), 기본 단가(`DEFAULT_PRICES`)가 코드 상수. 설정 화면 선택 목록도 코드에 박혀 있음.
- 단종·변경 시 코드 수정 + 재배포가 필요한 구조입니다.

### 7.2 설계: `model_registry` + `model_slots`

```sql
create table model_registry (
  id            integer primary key,
  capability    text not null,      -- text | vision | image | tts | video | embedding
  vendor        text not null,      -- gemini | anthropic | openai | (확장)
  model_id      text not null,      -- 공급자 API가 받는 정확한 모델 문자열(버전 포함)
  display_name  text not null,
  price_in      real,               -- 100만 토큰당 입력 단가(USD) — 텍스트/비전
  price_out     real,               -- 100만 토큰당 출력 단가
  price_per_image   real,           -- image
  price_per_second  real,           -- video, tts(초당) 등
  price_per_unit    real, unit text,-- 그 밖 단위(예: 1천 자)
  enabled       integer default 1,
  note          text,               -- 예: "2026-12-31까지 프로모션 가격"
  updated_at    text,
  unique (vendor, model_id, capability)
);
create table model_slots (          -- 기능별로 어떤 모델을 쓸지
  slot      text primary key,       -- blog_text | card_plan | shorts_script | vision | card_image | tts | video | translate…
  model_ref integer references model_registry(id),
  fallback_ref integer references model_registry(id)   -- 선택 사항
);
```

- **단가가 없으면 null = '단가 미등록'** 으로 표시하고 0으로 채우지 않습니다(cjc 규칙 유지). 앱에는 모델 목록의 **예시(seed)** 를 넣되 단가는 비워 두고, 사용자가 공식 요금표를 보고 입력합니다.
- 금액은 호출 시점 단가로 `usage_log.cost_usd` 에 저장(과거 기록이 단가 수정으로 변하지 않음). card_shorts 방식(수정 시 과거 재계산)과 달라서 cjc 방식으로 통일.
- 설정 화면: 용도별 탭(텍스트/이미지/영상/음성) → 행 추가·수정·사용 여부, **[연결 테스트]**(cjc `test_connection` 확장: 해당 모델로 최소 호출).
- 모델 호출 실패가 "모델 없음/단종"류이면 조용히 다른 모델로 바꾸지 않고, 슬롯 이름과 함께 **"설정 > 모델에서 변경하세요"** 로 안내(사용자가 고른 모델은 자동 대체 안 함 — card_shorts 정책). `fallback_ref` 를 사용자가 지정했을 때만 대체.
- 공급자 어댑터는 `capability` 별 인터페이스로 분리: `TextProvider.generate`, `VisionProvider.describe`, `ImageProvider.generate/edit`, `TtsProvider.speak`, `VideoProvider.animate`. 새 공급자는 어댑터 1개 추가.
- 모델별 특이사항(예: Anthropic의 파라미터 형식, Gemini thinking 설정)은 어댑터 내부에서만 처리하고, 등록 화면에는 "고급 옵션(JSON)" 칸으로 노출.

## 8. 네이버 API·광고주 정보: 선택 사항으로 해도 되는가

### 8.1 현재 사용 범위 (cjc 코드 기준)
두 종류의 별개 인증이 있고, **둘 다 오직 "SEO 키워드 점수"에만** 쓰입니다.

| 인증 | 어디서 받나 | 쓰임 |
|---|---|---|
| ① 네이버 오픈 API (Client ID/Secret) | 네이버 개발자센터 앱 등록 | 키워드별 블로그 문서 수(경쟁도), 데이터랩 검색 추이 |
| ② 검색광고 API (Customer ID·액세스 라이선스·비밀키) | 네이버 광고주센터(광고시스템 → 도구 → API) | 키워드별 월간 검색량 |

- `seo_optimizer`: 점수 = 검색량 ÷ 경쟁도(`golden_score`). **검색량과 문서 수 둘 다 측정돼야** 점수가 나오고, 하나라도 없으면 0점이 되어 "초안에 쓰인 빈도"로 대체됩니다.
  코드 주석에 "API 장애가 초안 실패로 이어지지 않게" 한다고 적혀 있어, 자격이 없어도 **글 생성이 막히는 구조는 아닙니다**(코드 읽기 기준, 실제 미등록 상태 실행은 확인 필요).
- 네이버 게시 자동화(Playwright)는 위 API와 **무관**합니다(로그인 세션만 사용).

### 8.2 결론
**선택 사항으로 두어도 핵심 기능(블로그·카드·쇼츠 생성)에는 문제가 없습니다.** 다만 잃는 것이 있습니다.

| 없을 때 잃는 것 | 대안 |
|---|---|
| 데이터 기반 키워드 우선순위(검색량·경쟁도) | 브랜드 킷의 **시드 키워드 조합**. 문서에 이미 규칙이 있음: 거점(성산구/동읍) × 타깃·증상 × 온자람 솔루션 키워드 1개씩 → 자동 조합 |
| "황금 키워드" 발굴(새 키워드 탐색) | 월 1회 담당자(개발자)가 측정해서 결과만 배포(아래 ③) |

### 8.3 제안: 3단계 + 설정 부담 제거
1. **레벨 0 (기본, 키 없음)**: 킷의 키워드 풀 + 시드 조합 사용. 설정 화면에 네이버 항목은 접혀 있고 "선택 사항" 표시.
2. **레벨 1 (API HUB만)**: cjc 코드가 쓰는 것은 개발자센터 오픈 API가 아니라 **네이버 클라우드 플랫폼(NCP) API HUB**(블로그 검색 문서 수·검색어트렌드)입니다. 키 2개(Client ID/Secret)이고 광고 집행은 필요 없지만 **NCP 계정·API 신청이 필요**해 설정 난이도가 낮지 않습니다(앞서 '개발자센터 앱 등록'이라 적은 것은 부정확했음). 검색량이 없으면 검색 추이(상대값)÷경쟁도, 그것도 없으면 문서 수만으로 점수화합니다(구현됨).
3. **레벨 2 (검색광고 API 추가)**: 현행 전체 기능. 광고주 계정·API 라이선스가 필요해 사용자 난이도가 가장 높음 → 담당자 1명이 한 번만.
- ③ **배포용 일괄 설정 (확정)**: cjc의 📦 데이터 옮기기(`core/transfer.py`)와 **같은 방식**으로 구현합니다. 개발자 PC에서 키·키워드 측정 캐시 등을 비밀번호로 암호화한 `.osmu` 파일로 내보내고, 직원 PC는 가져오기로 받습니다. 직원이 API를 직접 만지지 않음.
  - 이식 범위: cjc의 항목(브랜드 킷·회사 공통·앱 설정·API 키·AI 비용 설정·키워드 측정값·제목 이력)에 이 앱의 **모델 등록·모델 슬롯, 카드 종류 팩 설정**을 추가. 새 테이블은 `transfer.TABLE_PARTS` 에 옮길지 여부를 반드시 등록(cjc의 시험이 강제).
  - cjc 규칙 유지: API 키는 평문으로 쓰지 않고 비밀번호로 암호화, `.master_key` 는 옮기지 않음, 가져오기는 한 트랜잭션이며 직전 DB를 `backups/` 에 복사, 항목은 이름으로 맞춤.
  - 공개 저장소이므로 `.osmu` 파일과 비밀번호는 저장소·설치 파일에 넣지 않고 별도 경로로 전달.
  - 비용: 네이버 API는 무료 한도가 충분해 비용 부담은 크지 않다고 판단(사용자 확인). 일일 호출 한도 표시·`naver_api_calls` 기록은 유지.
- **기능 끄기(disable) 스위치**: 설정 > 선택 기능에 `네이버 키워드 측정 사용` 토글(`app_settings`).
  - 꺼짐(키가 없을 때의 기본값): 키워드 측정·"SEO 키워드 새로 고르기"·API 호출 횟수 표시 등 관련 화면과 버튼을 숨기고 모든 호출을 건너뜀. 글 생성은 킷의 시드 키워드로 진행.
  - 켜짐인데 키가 없거나 인증 실패: 오류로 막지 않고 "키워드 측정 안 됨 — 시드 키워드 사용" 한 줄만 표시.
  - 근거: cjc의 글 생성 경로(`seo_optimizer`)는 API를 직접 부르지 않고 **캐시에 저장된 측정값만 읽으며**, 없으면 0점으로 처리합니다. 실제 API 호출은 사용자가 설정 화면에서 누르는 측정 버튼에서만 일어납니다(코드 읽기 기준, 키 없이 실행해 확인 필요).
  - 끄기 전에 측정해 둔 값(`keyword_cache`)은 지우지 않고 계속 활용. 네이버 게시 자동화는 이 스위치와 별개.
- **UI 개선**: 현재의 긴 단계 안내 문구(설정 화면에 수십 줄)를 "건너뛰기" 가 기본인 마법사로 줄이고, 연결 테스트 결과를 초록/회색 한 줄로 표시.
- 같은 원리로 **LLM 키도 최소 1개만 있으면 시작**하도록 첫 실행 마법사를 둡니다.

## 10. 모델 전략 질문(Gemini 전용 vs 멀티) — 권고

**텍스트는 멀티, 이미지·음성·영상은 1차 Gemini 전용**을 권합니다.

- 이유 1 — **영상·이미지·TTS 파이프라인은 이미 Gemini 기반**으로 구현·검증돼 있습니다(`image_generator`, `tts_gemini`, `omni_video`). Claude는 이미지·음성·영상을 생성하지 못하므로(card_shorts README에도 명시) 이 구간은 어차피 다른 공급자가 필요합니다.
- 이유 2 — **글쓰기는 고객 선호가 갈립니다.** 온자람이 블로그 글에 Claude를 쓰고 싶어 할 수 있고, `cjc` 라우터가 이미 Gemini·OpenAI·Claude 텍스트를 지원합니다. 슬롯 구조(§7)에서 `blog_text` 만 Claude로 두고 `card_plan` 은 Gemini로 둘 수 있습니다.
- 이유 3 — 모델 등록 시스템이 있으면 "멀티" 의 추가 비용은 **어댑터 유지보수**뿐입니다. 하지만 공급자를 늘릴수록 키 발급·결제 계정·오류 대응이 사용자 부담이므로, 사용자는 **Gemini 키 하나로 시작**하고 Claude/OpenAI 키는 선택으로 두는 게 맞습니다.
- OpenAI 이미지·영상: 어댑터 인터페이스만 열어 두고 1차 구현에서 제외(검증 부담). 필요해지면 `ImageProvider` 구현 하나로 추가.
- 운영 팁: 모델을 바꿔 가며 같은 원고로 결과와 비용을 비교(card_shorts에 있는 기능)하는 화면을 유지.
- 현재 모델 이름·가격은 제가 임의로 확정하지 않습니다. 레지스트리에서 사용자가 공식 문서를 보고 입력합니다(코드 규칙: 가격 기본값 하드코딩 금지).

## 12. Windows 배포

- cjc의 GitHub Actions(`flet build windows` + Inno Setup) 구조를 재사용. `AppId` GUID는 **새로 발급 후 고정**.
- **FFmpeg·ffprobe 동봉 필요**: card_shorts는 시스템 설치를 가정함(`shutil.which`, macOS brew 안내). 설치 폴더에 번들하고 라이선스(LGPL 빌드 여부) 확인. 설치 폴더는 쓰기 금지이므로 임시·출력은 `%APPDATA%\OSMU_Onjaram` 로.
- 폰트·아이콘 세트 동봉(라이선스 고지 포함). 큰 폰트는 용량 때문에 별도 폴더 방식 유지 가능.
- 공개 저장소이므로 cjc와 같이 `main` push 시 GitHub Release 자동 게시 구조를 쓸 수 있습니다(브랜치 push는 artifact만).

### 12.1 공개 저장소 규칙
- 커밋 금지: API 키, `.master_key`, `.osmu` 전송 파일, DB(`data/`), 내담자 관련 자료, 네이버 로그인 세션, 실제 업로드 사진.
- `info/`(회사 워드 문서·사진)는 `.gitignore` 에 넣습니다. 사업자번호·연락처·가격 같은 공개 가능한 사업 정보도 저장소 코드에는 **시드 파일 하나(`core/brand_seed.py`)** 로만 두고, 문서 원문은 올리지 않습니다.
- 대표자명·상담사명·내담자 사례는 시드에 넣지 않습니다. 개인정보가 섞이지 않는지 첫 커밋 전에 점검합니다.
- 쇼츠 렌더는 CPU·시간이 큼 → 백그라운드 스레드·진행률·취소 지원.
